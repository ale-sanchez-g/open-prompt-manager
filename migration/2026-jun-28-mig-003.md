# MIG-003: Secrets Manager rotation & RDS IAM authentication

## Summary

This is an **infrastructure migration** (Terraform), not a database schema
change. It implements [issue #202](https://github.com/ale-sanchez-g/open-prompt-manager/issues/202):

1. Enables IAM database authentication on the RDS instance
   (`iam_database_authentication_enabled = true`). Additive — the application
   continues to use password authentication.
2. Adds automatic rotation of the `DATABASE_URL` secret via a custom in-VPC
   Lambda (`aws_secretsmanager_secret_rotation`), default cadence 30 days.
3. Removes the `CKV_AWS_161` and `CKV2_AWS_57` SAST suppressions.

Full rationale and trade-offs: [`docs/adr-secrets-rotation-iam-auth.md`](../docs/adr-secrets-rotation-iam-auth.md).

## Architecture Check

### What is sound

- IAM auth is **additive**: enabling it does not change how the master user (and
  therefore the application) authenticates. No application change is required.
- Rotation rewrites the existing `DATABASE_URL` connection-string secret in
  place, so the `DATABASE_URL` ECS-secret contract is unchanged.
- The rotation Lambda runs in private subnets with a least-privilege role,
  reaching only RDS (5432) and the AWS APIs (443). Invocation is restricted to
  the Secrets Manager service principal and the single secret ARN.
- The only Lambda dependency is `pg8000` (pure Python) — no native build step.

### Operational requirement

- The rotation Lambda package must be built **before** `terraform apply` so the
  archive contains `pg8000`. `deploy.sh` and the deploy workflow do this; manual
  applies must run `terraform/lambda/db_rotation/build.sh` first.
- `iam_database_authentication_enabled` triggers a short RDS modification; it is
  applied without a reboot and without data loss.

### Risks

- **Connection-pool staleness (single-user rotation).** When the password
  rotates, ECS tasks holding pooled connections opened with the old credentials
  fail on reconnect until recycled (they cache `DATABASE_URL` from task start).
  Mitigation: force a fresh ECS deployment after an out-of-band rotation, or
  migrate the app to IAM-token auth (now enabled). The scheduled 30-day rotation
  should be paired with a maintenance-window redeploy until the app adopts IAM
  auth.
- Applying to an existing instance with `db_deletion_protection = false` and a
  pending password change is safe and reversible (Terraform re-derives the
  secret from `random_password.db_password`).

## Deployment Steps

### Automated via `deploy.sh` (default path)

`prepare_terraform_workspace` builds the rotation Lambda package before any
`terraform apply`. No extra action is needed:

```bash
./deploy.sh
```

### Manual Terraform

```bash
terraform/lambda/db_rotation/build.sh        # vendor pg8000 into the package
cd terraform
terraform init
terraform apply
```

## Validation Checklist

```bash
# 1. IAM auth is enabled on the instance
aws rds describe-db-instances \
  --db-instance-identifier open-prompt-manager-prod \
  --query 'DBInstances[0].IAMDatabaseAuthenticationEnabled'      # -> true

# 2. Rotation is configured on the secret
aws secretsmanager describe-secret \
  --secret-id open-prompt-manager/prod/database-url \
  --query '{RotationEnabled:RotationEnabled,Days:RotationRules.AutomaticallyAfterDays}'

# 3. Rotation executes successfully (non-prod first)
aws secretsmanager rotate-secret \
  --secret-id open-prompt-manager/prod/database-url
#    then confirm the app still connects (it re-reads DATABASE_URL on new tasks):
aws ecs update-service --cluster open-prompt-manager-cluster \
  --service open-prompt-manager-backend --force-new-deployment
```

- `IAMDatabaseAuthenticationEnabled` is `true`.
- `RotationEnabled` is `true` and `AutomaticallyAfterDays` is `30`.
- A manual `rotate-secret` completes (status `Successfully`); the backend
  reaches the DB after the forced redeployment.
- `terraform fmt -check -recursive`, `terraform validate`, `terraform test`,
  and the Checkov fail-policy gate pass with the suppressions removed.

## Rollback

- **IAM auth:** set `iam_database_authentication_enabled = false` and apply.
  Non-destructive; the application is unaffected either way.
- **Rotation:** remove `aws_secretsmanager_secret_rotation.db_url` (or run
  `aws secretsmanager cancel-rotate-secret`). The current `DATABASE_URL` value
  remains valid.
- Re-adding the two register suppressions reverts the SAST posture if required.

## Follow-up

- Application support for IAM-token DB authentication (removes static-password
  dependence and eliminates the connection-pool staleness trade-off).
- Overlapping JWT signing-key window so `JWT_SECRET` rotation can be enabled and
  its inline Checkov skip removed.
