# MIG-002: Add `users.role`

## Summary

This change adds a `role` column to the `users` table to support role-based access control (RBAC). Two roles are recognised: `admin` and `user`. The role is embedded in the JWT access token and enforced by the API for the admin endpoints under `/api/admin/*`.

The application code assumes this column exists in the `User` ORM mapping. Without it, login and any request that serialises a user can fail with:

```text
sqlite3.OperationalError: no such column: users.role
```

## Architecture Check

### What is sound

- The schema change is additive only. It does not drop or rewrite existing data.
- The column has a default of `user`, so existing rows remain valid without backfill.
- The migration promotes the earliest-created account to `admin` **only when no admin already exists**, so an upgraded instance is never left without an administrator.
- The migration is idempotent: if the column already exists, it exits without altering the schema (returns `False`), while still repairing NULL roles and ensuring an admin exists.
- The same script works for local SQLite and AWS PostgreSQL because the `ALTER TABLE ... ADD COLUMN ... DEFAULT 'user'` syntax is supported by both.

### Main architectural constraint

- This repository does not currently use a migration framework.
- `Base.metadata.create_all()` only creates missing tables. It does not alter existing tables.
- Because of that, code and database schema can drift, and application startup will not repair the drift.

### Operational requirement

- The migration must run before deploying application code that reads `users.role`.
- Do not rely on app startup to perform this change, especially in ECS where multiple tasks may start concurrently.

### Risks

- If new backend code is deployed before the migration, login and user serialisation can fail.
- If the migration is executed concurrently by multiple processes, there is a race between the column existence check and `ALTER TABLE`.
- Rollback after code deploy is safe because the change is additive.

### Recommendation

- Treat this as a manual pre-deploy migration.
- Run it once per environment.
- Verify the column exists, and confirm exactly one (or the intended) admin account before shifting traffic.

## Implementation

Migration script:

- `backend/migrations/add_user_role.py`

Behavior:

1. Connects using `DATABASE_URL`.
2. Adds `users.role` with default `user` if missing.
3. Backfills any NULL roles to `user`.
4. Promotes the earliest-created account to `admin` if no admin exists.

## Deployment Steps

### Local Docker

```bash
cd <repo-root>
docker-compose up -d --build
docker-compose exec -T backend python -m migrations.add_user_role
docker-compose exec -T backend python - <<'PY'
from app.database.base import SessionLocal
from sqlalchemy import text

db = SessionLocal()
try:
    cols = db.execute(text("PRAGMA table_info(users)")).fetchall()
    print([c[1] for c in cols])
finally:
    db.close()
PY
```

Expected result:

- `role` appears in the `users` columns list.

### AWS ECS + RDS PostgreSQL

**Automated via `deploy.sh` (default path).** Step 8 of the deployment script
runs this migration automatically after Terraform rolls out the new backend
image. It calls the reusable runner:

```bash
PROJECT_NAME=open-prompt-manager AWS_REGION=<region> CLUSTER_NAME=<cluster> \
FORCE_NEW_DEPLOYMENT=true \
  ./scripts/migration/run_aws_migration.sh \
    migrations.add_agent_updated_at migrations.add_user_role
```

The runner launches each migration module as a one-off ECS Fargate task using
the backend service's task definition (same image, `DATABASE_URL` secret, and
private subnets/security groups), waits for it to stop, and fails the deploy if
any migration returns a non-zero exit code. `FORCE_NEW_DEPLOYMENT=true` then
replaces the backend tasks so the steady state always runs against the upgraded
schema.

**Manual execution.** To run this migration on its own, use the dated wrapper or
the runner directly from an operator machine with AWS credentials:

```bash
AWS_REGION=<region> ./scripts/migration/2026-jun-20-aws-mig-002.sh
# equivalently:
AWS_REGION=<region> ./scripts/migration/run_aws_migration.sh migrations.add_user_role
```

Alternative options:

1. Open a shell in a backend task/container and run `python -m migrations.add_user_role`.
2. Or run it from an operator machine only if `DATABASE_URL` is explicitly pointed at the AWS RDS instance.

PostgreSQL verification query:

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 'users'
ORDER BY ordinal_position;
```

Admin verification query:

```sql
SELECT COUNT(*) AS admin_count
FROM users
WHERE role = 'admin';
```

Expected result:

- `role` exists.
- `admin_count >= 1`.

## Rollback

Application rollback:

- Safe. The added column is backward compatible with older code.

Database rollback:

- Usually unnecessary for this change.
- If absolutely required, dropping a column should be handled as a separate, explicit maintenance task.

## Validation Checklist

- Migration script is present in the deployed backend image.
- Migration executed successfully in the target environment.
- `users.role` exists.
- At least one account has `role = 'admin'`.
- `POST /auth/login` returns `200` and the access token contains a `role` claim.
- `GET /api/admin/users` returns `200` for an admin and `403` for a standard user.

## Follow-up Architecture Recommendation

As noted in MIG-001, the underlying issue is the lack of schema migration management. The next architectural step should be to introduce a real migration workflow (e.g. Alembic) so additive schema changes such as this one are versioned, reviewable, and applied consistently across local, Docker, and AWS environments.
