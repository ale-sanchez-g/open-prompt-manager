# MIG-003: Restricted security-group egress and VPC endpoints

## Summary

This change removes all unrestricted (`0.0.0.0/0`) egress from the
application security groups, blocks internet HTTP (port 80) ingress on the
ALB by default, and introduces VPC endpoints (interface endpoints for
ECR api/dkr, CloudWatch Logs, SSM Parameter Store, Secrets Manager, STS, KMS,
plus an S3 gateway endpoint) so ECS task traffic to AWS APIs stays inside the
VPC.

It is an infrastructure-only change: no application code or database schema
is affected. It does, however, change live network behaviour, so upgrades of
an existing environment should follow the steps below.

## Behaviour changes

- **HTTP (port 80) from the internet is blocked by default.** The HTTP
  listener still exists, but the ALB security group only admits port 80 from
  the CIDRs in `var.alb_http_ingress_cidrs` (empty by default, `0.0.0.0/0`
  rejected by validation). Clients must use HTTPS, or trusted ranges must be
  listed explicitly while plaintext HTTP is still needed.
- **ECS tasks can no longer reach arbitrary internet destinations.** Egress
  is limited to in-VPC AWS endpoints, S3 via the gateway prefix list, RDS
  (backend only), and DNS. If the application later needs an external API,
  a dedicated egress rule (or proxy) must be added deliberately.
- **AWS API traffic no longer traverses the NAT Gateway.** The NAT Gateway
  is retained for now but is effectively idle; removing it is a possible
  follow-up cost optimisation.

## Deploy tooling

- `./deploy.sh` accepts a repeatable `--http-cidr <range>` flag that feeds
  `var.alb_http_ingress_cidrs`, and warns when HTTPS is disabled and no
  ranges are given (the app would be unreachable from the internet).
- The tag-triggered deploy workflow (`.github/workflows/deploy.yml`) reads
  the optional repository variable `ALB_HTTP_INGRESS_CIDRS` (JSON list,
  e.g. `["203.0.113.0/24"]`). Leave it unset for HTTPS-only.

## Upgrade steps for an existing environment

The security-group tightening and the endpoints land in the same plan.
Interface endpoints take several minutes to become `available`, so on a live
environment create them **before** the security groups drop their allow-all
egress, otherwise new task launches, log delivery, and secret fetches can
fail in the gap:

```bash
cd terraform

# 1. Create the endpoints and their security group first.
terraform apply \
  -target=aws_security_group.vpc_endpoints \
  -target='aws_vpc_endpoint.interface' \
  -target=aws_vpc_endpoint.s3

# 2. Wait until all interface endpoints report "available".
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values=<vpc-id> \
  --query 'VpcEndpoints[].{svc:ServiceName,state:State}'

# 3. Apply the full configuration (tightens the security groups).
terraform apply
```

A fresh environment needs no special ordering — a single
`terraform apply` converges correctly because Terraform orders the
security-group rules after the endpoints they reference.

## Validation

- Force a new deployment and confirm tasks start, pull images, and log:
  `aws ecs update-service --cluster <cluster> --service <backend-svc> --force-new-deployment`
- Confirm the app responds over HTTPS and the API can read its secrets
  (login works ⇒ `DATABASE_URL`/`JWT_SECRET` fetch works).
- Confirm internet HTTP is refused: `curl -m 10 http://<alb-dns>/` should
  time out unless the source is listed in `alb_http_ingress_cidrs`.

## Rollback

`git revert` the change and `terraform apply`. The endpoints are removed
and the previous allow-all egress rules are restored; no data is affected.
